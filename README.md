# CivicFix AI — Smart Public Complaint Chatbot

An AI chatbot that lets citizens report public problems — potholes, garbage accumulation, water
leakage, broken streetlights and damaged roads — in plain language, then track each complaint until
it is resolved. Administrators get a searchable dashboard where every status change is audit-logged.

Built as a full-stack MERN application with a React + Vite + Tailwind frontend, an Express + MongoDB
backend, and an OpenAI-powered chatbot layer that degrades to a clearly-labelled rule-based engine
when no API key is present.

## 1. Features

### Authentication
- Citizen registration and login.
- Passwords hashed with **bcrypt** (12 rounds) — never stored in plain text.
- **JWT**-based sessions; the token is re-validated against MongoDB on every request.
- Separate protected citizen and administrator areas.
- Role-based access control enforced on the backend, not just hidden in the UI.
- Self-registration can never create an administrator.

### AI chatbot
- Accepts free-form natural language.
- Distinguishes **reporting an issue** from **checking a complaint status**.
- Extracts category, description and location; asks for whatever is missing (location first).
- Shows a structured summary and only files the complaint after explicit confirmation.
- Returns the **real tracking ID generated by the backend**.
- Model is configurable via `OPENAI_MODEL`.
- Clearly-labelled **rule-based demo mode** when `OPENAI_API_KEY` is absent, and an automatic
  graceful fallback if the OpenAI call fails mid-session.
- **Never invents** complaint records, tracking IDs or status updates — the model has no database
  access at all; every status answer is a live MongoDB lookup.

### Complaint lifecycle
- Unique tracking IDs in the form `CIV-YYYY-XXXXXX` (no look-alike characters).
- Statuses: **Submitted → In Progress → Resolved**, validated on the backend.
- Full `statusHistory` audit trail recording who changed the status, their role, when, and an
  optional note.
- Citizens see only their own complaints; administrators see everything.

### Citizen dashboard
- Live counts by status, read from MongoDB via aggregation (nothing hardcoded).
- Recent complaints, search by tracking ID, status filters.
- A button to start a new chatbot conversation.
- Complaint detail page with the complete status timeline.

### Administrator dashboard
- Summary cards for submitted / in-progress / resolved.
- Searchable, filterable table (status, category, free text) with sorting and pagination.
- Details dialog with status update form and the full audit history.
- Every update records the administrator and a timestamp.

### UI
- Light civic-tech theme, brand blue + teal accents, Inter typography.
- Responsive from mobile to desktop.
- Loading skeletons, inline error messages, empty states, toast notifications.
- Accessible: labelled inputs, focus rings, keyboard-dismissible dialog, ARIA roles.

## 3. Architecture

```
                     ┌──────────────────────────────────────────┐
   Browser  ───────► │  nginx  (frontend container, port 80)     │
                     │   • serves the compiled React SPA         │
                     │   • proxies /api/* ─────────┐             │
                     └─────────────────────────────┼─────────────┘
                                                   ▼
                     ┌──────────────────────────────────────────┐
                     │  Express API  (api container, port 5000)  │
                     │   routes → controllers → services         │
                     │          ↘ middleware (auth, validate)    │
                     │          ↘ models (Mongoose) ─────┐       │
                     └───────────────────────────────────┼───────┘
                                       │                 │
                        OpenAI SDK  ◄──┘                 ▼
                     (server-side only)        ┌──────────────────┐
                                               │  MongoDB 7       │
                                               │  users,         │
                                               │  complaints     │
                                               └──────────────────┘
```

**Key design decision — the AI never touches the database.**

The chatbot is split into two halves:

1. `services/aiService.js` turns natural language into a **structured intent** object. It has no
   database access and is instructed, in the system prompt, never to invent records or IDs.
2. `services/chatService.js` owns all business logic: merging the draft, deciding what is still
   missing, looking up **real** complaints for status questions, and deciding when a summary may be
   submitted.

A complaint is written to MongoDB in exactly one place: `POST /api/complaints`, and only after the
citizen presses **Confirm**. This is what makes "never invent a tracking ID" a structural guarantee
rather than a prompt request.

**Stateless chat.** The client echoes back the current `draft` and the last few turns with each
message, so the API holds no per-conversation server state.

## 5. Quick start with Docker

**Prerequisites:** Docker Desktop (with WSL 2 enabled on Windows).

```bash
cd civicfix-ai
cp .env.example .env          # Windows PowerShell: Copy-Item .env.example .env
```

Edit `.env` and set at minimum a real `JWT_SECRET`:

```bash
node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"
```

Then:

```bash
docker compose up --build
```

| Service  | URL                              |
| -------- | -------------------------------- |
| Frontend | http://localhost:8080            |
| API      | http://localhost:5000/api/health |
| MongoDB  | localhost:27017 (admin / your `MONGO_ROOT_PASSWORD`) |

The administrator account is created automatically at startup because `SEED_ADMIN_ON_START=true`:

```
admin@civicfix.ai  /  Admin@12345
```

Useful commands:

```bash
docker compose logs -f api      # follow API logs
docker compose exec api node src/scripts/seedAdmin.js   # re-seed the admin
docker compose down             # stop
docker compose down -v          # stop and delete the database volume
```

## 6. Quick start without Docker

**Prerequisites:** Node.js 18+ and a MongoDB instance (local install or a free MongoDB Atlas cluster).

### 6.1 Get a database

Pick one:

- **MongoDB Atlas (no install):** create a free M0 cluster, add a database user, allow your IP, and
  copy the connection string:
  `mongodb+srv://<user>:<password>@<cluster>.mongodb.net/civicfix`
- **Local MongoDB:** `mongodb://127.0.0.1:27017/civicfix`

### 6.2 Backend

```bash
cd backend
cp .env.example .env          # then edit MONGODB_URI and JWT_SECRET
npm install
npm run seed                  # creates the administrator account
npm run dev                   # http://localhost:5000
```

### 6.3 Frontend

In a second terminal:

```bash
cd frontend
cp .env.example .env          # defaults work as-is
npm install
npm run dev                   # http://localhost:5173
```

Vite proxies `/api` to `http://localhost:5000`, so no CORS configuration is needed in development.

### 6.4 Or run both from the repository root

```bash
npm run install:all
npm run dev                   # starts api + web together (uses concurrently)
```

| Command             | Effect                                        |
| ------------------- | --------------------------------------------- |
| `npm run dev`       | API + frontend concurrently                   |
| `npm run dev:api`   | API only                                      |
| `npm run dev:web`   | Frontend only                                 |
| `npm run build`     | Production frontend build → `frontend/dist`   |
| `npm run seed`      | Create/update the administrator account       |
| `npm test`          | Run the backend test suite                    |

### 6.5 Demo walkthrough

1. Open http://localhost:5173 and click **Create free account**. Register as a citizen.
2. Click **Report a new problem** and type: *"There is a large pothole on MG Road near the bus stop"*.
3. Answer the follow-up questions until the summary card appears.
4. Press **Confirm & submit complaint**. A tracking ID (e.g. `CIV-2026-A7K3P9`) is returned.
5. Log out, log in as `admin@civicfix.ai` / `Admin@12345`.
6. In the admin dashboard, click **Manage** on the complaint, set the status to **In Progress** with a
   note, and save.
7. Log back in as the citizen and open the complaint — the status and note are there.

#### Using a free AI provider instead of OpenAI

The AI layer speaks the OpenAI Chat Completions protocol, so you can point it at any
OpenAI-compatible provider's free tier via `OPENAI_BASE_URL`:

| Provider        | `OPENAI_BASE_URL`                                          | Example `OPENAI_MODEL`        |
| --------------- | ---------------------------------------------------------- | ----------------------------- |
| Google Gemini   | `https://generativelanguage.googleapis.com/v1beta/openai/` | `gemini-flash-latest`         |
| Groq            | `https://api.groq.com/openai/v1`                           | `llama-3.3-70b-versatile`     |
| OpenRouter      | `https://openrouter.ai/api/v1`                             | `meta-llama/llama-3.1-8b-instruct:free` |
| Ollama (local)  | `http://localhost:11434/v1`                                | `llama3.2:3b`                 |

Set `OPENAI_API_KEY` to that provider's key (Ollama accepts any non-empty string).
If the provider rejects JSON mode, the backend transparently retries without it.

| `VITE_API_URL`      | `/api`                  | API base path or full URL                    |

## 8. Database models

### `User`

| Field         | Type     | Notes                                                    |
| ------------- | -------- | -------------------------------------------------------- |
| `name`        | String   | required, 2–80 chars                                     |
| `email`       | String   | required, unique, lowercased, validated                  |
| `password`    | String   | required, ≥8 chars, `select: false`, bcrypt-hashed       |
| `role`        | String   | `citizen` \| `admin`, default `citizen`, indexed         |
| `lastLoginAt` | Date     | updated on successful login                              |
| `createdAt` / `updatedAt` | Date | automatic                                    |

Indexes: unique index on `email`; index on `role`.
`toJSON` deletes `password` and `__v`, so a hashed password can never leak through an API response.

### `Complaint`

| Field           | Type       | Notes                                                    |
| --------------- | ---------- | -------------------------------------------------------- |
| `trackingId`    | String     | required, **unique**, `CIV-YYYY-XXXXXX`, uppercased      |
| `citizen`       | ObjectId   | ref `User`, required, indexed                            |
| `category`      | String     | enum: Pothole, Garbage, Water Leakage, Broken Streetlight, Damaged Road, Other |
| `description`   | String     | required, 10–1000 chars                                  |
| `location`      | String     | required, 3–200 chars                                    |
| `status`        | String     | enum: Submitted, In Progress, Resolved; default Submitted; indexed |
| `priority`      | String     | Low \| Medium \| High, default Medium                    |
| `source`        | String     | `chatbot` \| `form` \| `admin`                           |
| `statusHistory` | Array      | audit trail (see below)                                  |
| `lastStatusAt`  | Date       | updated on every status change                           |
| `resolvedAt`    | Date       | set when status becomes Resolved, cleared otherwise       |
| `createdAt` / `updatedAt` | Date | automatic                                      |

**`statusHistory` entry**

| Field           | Notes                                                       |
| --------------- | ----------------------------------------------------------- |
| `status`        | the status at that moment                                   |
| `note`          | optional administrator note (≤500 chars)                    |
| `changedBy`     | ObjectId ref `User` (null for system)                       |
| `changedByName` | denormalised snapshot of the actor's name                   |
| `changedByRole` | `citizen` \| `admin` \| `system`                            |
| `changedAt`     | timestamp                                                   |

Indexes: unique `trackingId`; `{ citizen, createdAt: -1 }`; `{ status, category }`;
`{ createdAt: -1 }`; text index on `description` and `location`.

## 9. API reference

Base URL: `http://localhost:5000/api`

All responses use the same envelope:

```json
{ "success": true, "message": "optional", "data": { } }
```

Errors:

```json
{ "success": false, "message": "Human readable", "errors": [ { "field": "email", "message": "…" } ] }
```

Authenticated requests need `Authorization: Bearer <token>`.

### Authentication — `/api/auth`

| Method | Path        | Access | Description                                    |
| ------ | ----------- | ------ | ---------------------------------------------- |
| POST   | `/register` | public | Create a citizen account → `{ user, token }`   |
| POST   | `/login`    | public | Log in (citizen or admin) → `{ user, token }`  |
| GET    | `/me`       | auth   | Current user for the supplied token            |

### Chatbot — `/api/chat`

| Method | Path        | Access | Description                                          |
| ------ | ----------- | ------ | ---------------------------------------------------- |
| GET    | `/mode`     | auth   | `{ aiMode, isDemoMode, notice, categories, statuses }` |
| GET    | `/greeting` | auth   | Opening assistant message                            |
| POST   | `/message`  | auth   | Interpret a message (see below)                      |

`POST /message` body:

```json
{
  "message": "there's a pothole on MG Road",
  "history": [{ "role": "user", "content": "hi" }],
  "draft": { "category": null, "description": null, "location": null }
}
```

Response `data`:

```json
{
  "reply": "…",
  "intent": "report | track | greeting | unclear",
  "aiMode": "openai | demo",
  "degraded": false,
  "demoNotice": null,
  "draft": { "category": "Pothole", "description": "…", "location": "MG Road" },
  "missingFields": ["location"],
  "readyToSubmit": false,
  "complaint": null
}
```

When the intent is `track` and a matching complaint exists, `complaint` contains the **real database
record** (the only way complaint data ever reaches the chatbot).

### Citizen complaints — `/api/complaints`

| Method | Path             | Access  | Description                                |
| ------ | ---------------- | ------- | ------------------------------------------ |
| POST   | `/`              | citizen | Create a complaint after confirmation       |
| GET    | `/`              | citizen | List own complaints (`status`, `category`, `q`, `page`, `limit`) |
| GET    | `/stats`         | citizen | Counts by status, by category, recent 5     |
| GET    | `/:trackingId`   | citizen | Own complaint details + status history      |

### Administrator — `/api/admin`

| Method | Path                                | Access | Description                              |
| ------ | ----------------------------------- | ------ | ---------------------------------------- |
| GET    | `/complaints`                       | admin  | All complaints (`status`, `category`, `q`, `sort`, `page`, `limit`) |
| GET    | `/complaints/:trackingId`           | admin  | Any complaint's details                  |
| PATCH  | `/complaints/:trackingId/status`    | admin  | `{ status, note? }` — audited            |
| GET    | `/stats`                            | admin  | Platform-wide summary                    |

### Infrastructure

| Method | Path      | Access | Description                                        |
| ------ | --------- | ------ | -------------------------------------------------- |
| GET    | `/health` | public | Status, DB state, AI mode, categories, statuses    |

### Status codes

| Code | Meaning                                                      |
| ---- | ------------------------------------------------------------ |
| 200  | OK                                                           |
| 201  | Created                                                      |
| 400  | Validation error (with `errors[]`)                           |
| 401  | Missing / invalid / expired token                            |
| 403  | Authenticated but the role is not allowed                    |
| 404  | Not found — also used when a citizen requests a foreign complaint |
| 409  | Duplicate email, or a tracking ID collision                  |
| 413  | Payload too large                                            |
| 429  | Rate limited                                                 |
| 500  | Unexpected server error                                      |

## 10. The chatbot flow

```
Citizen types a message
        │
        ▼
POST /api/chat/message  ──►  aiService.interpretMessage()
        │                        │
        │                        ├─ OPENAI_API_KEY set → OpenAI (JSON mode, temperature 0.2)
        │                        └─ otherwise / on error → rule-based keyword engine
        │                        │
        │                    returns { intent, category, description, location, trackingId, reply }
        ▼
chatService.handleChatMessage()
        │
        ├─ intent === "track"?
        │      └─ look up the complaint in MongoDB (scoped to the citizen)
        │         found     → reply contains the REAL status + history
        │         not found → "I could not find…" (never fabricates anything)
        │
        └─ otherwise merge the draft
               ├─ missing fields? → ask for location first, then description
               └─ complete?       → readyToSubmit: true, UI shows the summary card
        │
        ▼
Citizen presses "Confirm & submit"
        │
        ▼
POST /api/complaints  ──►  re-validated from scratch
                           unique tracking ID generated
                           complaint + initial history entry saved to MongoDB
                           tracking ID returned
```

**Readiness is decided by the server, not the model.** If the model's opinion disagrees with the
server's, the server replaces the reply with a deterministic one — so a citizen is never invited to
confirm a complaint that cannot actually be saved.

## 11. Security

| Concern                          | How it is handled                                                                 |
| -------------------------------- | --------------------------------------------------------------------------------- |
| AI key exposure                  | `OPENAI_API_KEY` lives only in backend env vars; it is never sent to the browser   |
| Plain-text passwords             | bcrypt, 12 rounds; `select: false` and a `toJSON` transform strip it from responses |
| Account enumeration              | Unknown email and wrong password return the same message and status                |
| Privilege escalation             | `role` is ignored on registration; admins exist only via the seed script            |
| Cross-citizen data access        | Ownership is part of the MongoDB query, so foreign complaints look "not found"      |
| Backend validation               | express-validator on every route **and** Mongoose schema validation                 |
| Administrator endpoints          | `protect` + `adminOnly` middleware on the entire `/api/admin` subtree              |
| Brute force                      | `express-rate-limit`: 30 auth attempts / 15 min, 30 chat messages / min            |
| Stored XSS                       | React escapes all interpolated content by default                                  |
| Clickjacking / MIME sniffing     | `helmet` on the API; `X-Frame-Options`, `X-Content-Type-Options` in nginx          |
| Large payloads                   | `express.json({ limit: '100kb' })` and a 1 MB nginx `client_max_body_size`         |
| Secrets in git                   | `.gitignore` excludes every `.env` variant; only `.env.example` is committed        |
| Error leakage                    | Stack traces are only returned outside production and never in tests               |

**Before deploying for real:** change `JWT_SECRET`, change `ADMIN_PASSWORD`, set `NODE_ENV=production`,
restrict `CORS_ORIGIN`, and delete the "Demo helper" block from `LoginPage.jsx`.

## 13. Troubleshooting

**`ECONNREFUSED` / `Server selection timed out` on startup**
MongoDB is unreachable. Check `MONGODB_URI`. With Docker: `docker compose up -d mongo` and wait for
the health check. With Atlas: confirm your current IP is allowed and the password is URL-encoded.

**Chatbot always says "Demo mode"**
`OPENAI_API_KEY` is empty or the OpenAI call failed. That is by design — the app is fully functional
without it. Check `GET /api/health` → `data.ai.mode`. If you set a key, restart the backend.

**`401 Authentication required` after logging in**
Tokens last `JWT_EXPIRES_IN` (default 7 days). Changing `JWT_SECRET` invalidates every existing
token — log in again.

**`403 Administrator access is required`**
You are logged in as a citizen. Log in with the seeded admin account, and create it with
`npm run seed` if you have not.

**`409 An account with this email address already exists`**
Use `/login`, or register with a different email.

**Complaint shows `404` for the right tracking ID**
The complaint belongs to another citizen. This is intentional — existence is not revealed. Log in as
an administrator to see every complaint.

**Port already in use**
Change `PORT` in `backend/.env`, `VITE_PROXY_TARGET` in `frontend/.env`, or `API_PORT` / `WEB_PORT`
in the root `.env` for Docker.

**Docker build is slow or fails on Windows/OneDrive**
Exclude the project folder from OneDrive sync, or move it outside a synced directory. OneDrive
frequently locks files inside `node_modules`, which breaks Docker build contexts.

**`ng` / `npm` not found**
Only Node.js 18+ is required. Docker and MongoDB are both optional if you use Atlas.

## 14. Out of scope

Deliberately excluded to keep the project medium-sized and easy to demonstrate:

- Image / photo recognition or attachments.
- Live maps or geocoding.
- Duplicate-complaint detection.
- Email or SMS notifications.
- Microservices, message queues or background workers.
- Refresh tokens, password reset and email verification.
- Multi-tenancy, multiple cities or departments.
